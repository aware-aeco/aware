# Plan: make `google-workspace.gmail.send` genuinely runnable (#495)
_Round 4 — revised after Codex review_

## Goal
Replace the advertised-but-undistributed `aware-google` executable with a Gmail send implementation that ships inside the AWARE binary, has explicit at-most-once failure semantics, returns unambiguous provider and RFC identifiers, and leaves every other unwired Google Workspace command honestly `planned`.

## Frozen command contract
- Inputs: `to[]`, optional `cc[]` / `bcc[]`, `subject`, `body`, `content-type` (`text` or `html`), and a required caller-stable `attempt-id`. File attachments are removed from the available v1 contract; arbitrary local paths are not admitted as a mail primitive.
- Sender: resolve the authenticated mailbox address in a pinned, pre-dispatch Google identity call and use it as `From`; do not accept an arbitrary sender in this change.
- Accepted output: `{status: "accepted", message-id, gmail-message-id, thread-id, rfc-message-id, attempt-id}`. For backward compatibility with FloLess #1090, `message-id` and `gmail-message-id` are the same bounded Gmail Message resource `id`; `rfc-message-id` is the separately generated RFC 5322 header value and is never presented as the Gmail resource ID.
- Failure taxonomy: validation/auth/identity failures occur before dispatch. Only 4xx responses that definitively reject the request are `gmail.send.rejected`; 408, 5xx, transport/read/parse failures, redirects, and a success body with no usable Gmail ID are `gmail.send.outcome-unknown`, with `retryable: false` and durable correlation details. No send path retries.
- The required `attempt-id` and canonical request hash are persisted and fsynced before dispatch. Reuse with different inputs is a conflict; an accepted identical attempt returns its cached output without another HTTP call; `dispatching` or `outcome-unknown` is refused with reconciliation details. This closes automatic/process replay for a logical attempt.

## Approach
1. Change the manifest from `cli`-first to REST-only, add exact Google identity/Gmail network permissions and OAuth2 auth, bump the manifest version, declare `gmail.send` irreversible, and mark the other 23 commands `planned`.
2. Narrow new Google OAuth grants to `openid`, `userinfo.email`, and `gmail.send`. Detect legacy broad Google grants before dispatch and fail closed with exact `aware disconnect google-workspace [--as=…]` then reconnect guidance; do not send with a token retaining the old Drive/Gmail-read/etc. blast radius. Gmail send also requires successful refresh, a nonblank token, and the exact required scopes before message construction. Correct the registration documentation: `gmail.send` is sensitive; `gmail.readonly` is restricted and is no longer requested by default.
3. Add a focused in-process Gmail module that bypasses generic REST response shaping. Compile-pin the two HTTPS origins and exact paths, disable redirects, and inject an HTTP-client trait only in tests so no manifest or environment override can redirect a production bearer token.
4. Use the maintained `mail-builder` crate to produce RFC 5322/MIME, including Date, authenticated From, CRLF-safe headers, encoded Unicode, a Bcc header in the submitted raw message (Gmail has no separate envelope API), and a pre-generated RFC Message-ID / `X-AWARE-Attempt-ID`. Verify output with the independent `mail-parser` crate and golden assertions. Enforce conservative recipient/header/body limits and a 1 MiB encoded-message ceiling before dispatch; JSON `raw` is retained because this no-attachment contract is intentionally bounded.
5. Resolve and hash the stable authenticated Google OIDC `sub` as the outbox account namespace; credential generation is record metadata only, so reconnecting the same account cannot bypass replay protection. Add an append-only journal at `~/.aware/outbox/google-workspace/<sha256(oidc-sub)>/<sha256(attempt-id)>.jsonl`, documented in `cli-spec.md` and the roadmap. The filename is never caller text. Use an exclusive `fs2` lock, create-new for the first record, file plus parent-directory durability barriers, and append+`sync_all` for terminal state.
6. Reuse the repository's private-directory/file machinery and strengthen it where necessary so every outbox component is a real, owner-only location: Unix mode/owner checks and Windows current-user ACL checks, failing closed before dispatch. Retain these small records until an explicit future GC command exists. Store no recipient/body/token plaintext; records contain hashed account/attempt keys, credential generation, request hash, correlation IDs, state, and timestamps.
7. Extend `StructuredAgentError` backward-compatibly with optional `details` carrying only bounded `attemptId` and `rfcMessageId`; test CLI envelopes, JSONL, and serde compatibility. Define connect/write/read and total 30-second request deadlines. Once handed off, timeout, task cancellation, or process death leaves `dispatching`/`outcome-unknown` and cannot retry; the blocking closure owns terminal journal writes. Include a slow-trickle test proving the total bound terminates and persists unknown state.
8. Add a `status: requires-runtime` enum variant plus a `minimum-cli-version` field to the agent contract. New CLIs parse the variant and enforce the version at registry/local install, compile, and run; v0.135.0 already rejects the unknown enum value instead of ignoring the new version field and routing through generic REST. Set the corrected Google agent to the first CLI version containing this handler and test with the actual tagged v0.135.0 binary. This workflow cuts no CLI release.
9. Add unit/integration tests for the frozen schema; narrow auth URL/scopes and legacy-grant migration; strict refresh; stable account namespace across credential rotation; origin/redirect pinning; MIME parsing; permissions; size/deadline limits; exactly one HTTP send; every response class including 408/5xx; journal concurrency/crash cases; accepted-cache replay; accepted-then-response-loss followed by same-attempt refusal; previous-CLI rejection; and the official manifest/catalog exposing only the implemented command.
10. Freeze the complete FloLess #1090 fixture in AWARE: request includes `attempt-id: floless-rfi-001-email-v1`, derived from the stable RFI identity and mail action; response asserts every identifier's semantics. Update the #495 reproducer to the same complete request. Document that FloLess must adopt this required field before enabling its pending integration; there is no existing shipped #1090 call site to preserve.
11. Add a QA runbook using a unique required `attempt-id` and controlled self/test recipient. A real canary must verify one matching RFC Message-ID / attempt marker in Sent and one in the recipient mailbox, verify Gmail stripped Bcc from the delivered copy, inspect decoded body/headers, and record the Gmail resource ID. A profile-only request, process exit 0, or node-output alone is not proof. Do not relabel `qa-ready` until that canary succeeds.
12. Publish the corrected agent as a new registry version whose tarball is pinned to an immutable implementation commit, preserve the rejected `1.0.0` entry/digest, update registry validation for commit-archive roots, update local test pins deliberately, regenerate catalog metadata, and test install/compile/run from the new entry.
13. Run fmt, clippy, all tests, the baseline missing-executable repro, and the same compiled app through the injected controlled client. Commit, run bounded self-feeding Codex code review, fix each finding with a specific test, push a PR with `Refs #495`, wait for final-commit CI/review, merge, and update the issue without cutting a release.

## Key decisions and limits
- The in-process path avoids a second unattested executable and uses the already distributed AWARE binary.
- No attachments ship in this fix. Artifact-handle attachment support can be added separately with an explicit filesystem capability and streaming limits.
- Gmail acceptance is not delivery. Unknown outcomes are deliberately non-retryable and human-reconciled using the durable attempt/RFC IDs.
- The generic REST transport, the global provenance format, and CLI rollback implementation are not redesigned here. The command declares irreversible semantics in the manifest; this fix adds focused validation/tests for that declaration without pretending the currently unimplemented `app rollback` command exists.
- FloLess product code is not modified here, but its current `message-id` expectation is frozen in an AWARE contract test and documented as Gmail resource-ID semantics.

## External blocker
This machine currently has no Google Workspace credential or user-approved recipient. Code, deterministic tests, registry install, and controlled transport verification can complete autonomously; the real-provider canary requires an explicitly authorized account/recipient. Until it succeeds, keep `qa-rejected` and report that precise blocker rather than claiming QA readiness.

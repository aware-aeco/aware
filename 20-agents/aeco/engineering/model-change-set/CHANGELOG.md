# Changelog

## 0.6.0 — 2026-11-23

- `check-snapshots` single mode runs clash on ONE saved state (floless.app #4029): with a clash rule, `revised-geometry-dir` is required and `base-geometry-dir`, `base-dir` and `coverage-base-path` stay refused. The earlier side is empty, so `resolvedInChange` is empty and every finding is `present`. Single-mode clash gives the verdicts pair mode gives the same state against an empty earlier state.
- Single mode takes an optional `focus-path` of exactly `{ identities }` (no `sets`) when the profile has a clash rule: clash then checks only pairs that involve those objects, their dependency closure or anything touching them, `scope.focus` becomes `{ requested, effective, unknown }` (0 without a focus) and `unchecked` says so. A requested identity that is not in the snapshot, or has no solid, is listed in `unknown` and counted in `scope.solids.noGeometry` (`not-in-snapshot` for the former). A focus or geometry with no clash rule is refused.
- Single-mode `unchecked` has no "unchanged parts" sentence; a profile without a clash rule reads "Clash checks were not run: the check profile has no clash rule."
- `geometry.minOverlap` (optional, >0 and >= `contactTolerance`, default `contactTolerance`): a report threshold only. Classification still uses `contactTolerance`; an overlap no thicker than `minOverlap` (unrounded) is measured but not listed, is never a contact finding, and when `minOverlap` is given is counted in `scope.byRule.<overlap rule>.belowThreshold { count, maxThicknessMm }` with an `unchecked` line. Pair mode too.
- `appliesTo.pairs` on a `clash-overlap` or `clash-contact` rule: the unordered type pairs that rule checks (each type must be in `types`; `[]` is refused; normalised and echoed). Applied before any budget and identically in the main pass and in pair re-checks (a left-out pair re-checks as `not-applicable`); left-out nearby pairs are counted per rule (`notEvaluated["pair-excluded"]` in v2, `pairExcluded` in v1) with an `unchecked` line. `clash-bolted-plies` is unaffected.
- Bounded broad phase: the candidate pairs are kept to `budgets.pairs` in a fixed (identity) order with memory bounded by the budget, whatever order the sweep meets them in. Not-evaluated reasons are now distinct: `pair-budget` (beyond the pair budget), `triangle-budget` (a solid or pair over a triangle limit; previously `over-budget`) and list truncation (`complete: false`). Pair-mode output changes only when a budget is hit.
- v2 documents with a clash rule echo `evaluator.geometry { contactTolerance, minOverlap, weldTolerance, budgets, pairs }`; `evaluator.version` reads `0.6.0`. Without `minOverlap`, `appliesTo.pairs` or a budget hit, pair-mode v1 output is byte-identical to 0.5.0 (pinned by golden files) and v2 differs only in its `evaluator` block.
- Needs connection-reader bridge 0.7.0 or newer.

## 0.5.0 — 2026-11-16

- `check-snapshots` gains `mode: "single"` (default `"pair"`): check ONE saved model version against a v2 check profile with scope `all`, with no earlier state. Every present violation is reported with `presence: "present"`; nothing is said about what changed or whether a finding is new. Inputs: `revised-dir`, `profile-path`, `check-profile-path`, optional `coverage-revised-path`. `base-dir`, `coverage-base-path`, `focus-path`, either geometry directory, a v1 check profile, a profile whose `scope` is not `all` and any clash predicate are refused (non-zero exit, message on stderr, nothing on stdout) rather than skipped. `validate-only` accepts `mode: "single"` and applies the same profile rules.
- Single-mode output is `aware.model-change-findings/v2` with a top-level `mode: "single"` (absent in pair mode, so pair output does not move): `inputs.base` and `coverageSha256.base` are null; `scope.added`, `changed` and `focus` are 0; every finding has `baseEvidenceFingerprint: null` and participants with `entityIdBase: null`; `resolvedInChange` and `focusResults` are empty; `summary` is `{ findings, present, byRule }`; per-rule `coverage.baseComplete` is null. Budgets and `truncated` work as in pair mode, and `summary.findings` equals the listed findings plus `truncated.omitted.findings`.
- One-object rules are judged by one shared function in both modes (`blank`, the property predicates, `relationship-missing`, the identity-key exclusion), so a single-mode verdict and its `notEvaluated` reason equal pair mode's judgement of the later state.
- Pair-mode output is unchanged except `evaluator.version`, which now reads `0.5.0`. `validate-only` also lists the `modes` this build supports.
- Needs connection-reader bridge 0.6.0 or newer (the bridge carries the code; an older bridge answers without `mode: "single"`, so a caller must check the echoed `mode` and `evaluator.version`).
- Folds in the unreleased #837 change below.

- `check-snapshots` (v2 profiles): a property rule whose key is the canonical key of a real identity row of either state is not evaluated, reason `key-is-identity`, instead of reporting every object as missing it (aware#834). The canonical key of each identity row is formed by the same function as every other row, so a key rule that builds it from `{name}` / `{groupName}` is followed exactly, and a shadowed (never used) key rule changes nothing. The exact-name rejection is unchanged. No manifest version change.

## 0.4.0 — 2026-11-14

- `check-snapshots` gains single-object rules from the data in a check profile of schema `aware.model-check-profile/v2` (v1 is still accepted, and a v1 profile produces the same v1 findings document, byte for byte): `property-missing`, `property-not-in` (`exact` or `nfkc-casefold`), `property-out-of-range` (`min` and/or `max`, with a unit; its worsening metric is `distanceOutside`) and `relationship-missing` (`to` or `from` end of a relationship kind). A rule gains strictly validated `parameters`; its `target` may be `property` or `relationship`; the profile gains `scope` (`changed`, the v1 behaviour and the default, or `all`: every applicable object of the later state, so a standard added today finds what was already there as pre-existing). `relationship-missing` always judges every applicable object, because a relationship is a fact about the whole object; each single-object rule echoes which in `scope.byRule.<rule>.evaluatedScope` (`all` | `changed`). Clash keeps its own scope.
- A property is found by its canonical key, after the comparison profile's `keyRules`, resolved by the code `compare-snapshots` uses.
- Not evaluated is not passed. A rule is judged for an object only when that side's read coverage affirmatively covers what the rule reads. New optional inputs `coverage-base-path` / `coverage-revised-path` take an `aware.model-read-coverage/v1` document (per entity id the property keys read completely, exact or `<prefix>:*`; per side the relationship kinds that are complete). Otherwise the object is counted per rule under `notEvaluated` with a reason: `coverage-not-supplied`, `source-did-not-read`, `value-missing`, `value-not-numeric`, `unit-mismatch`, `key-ambiguous`, `identity-unusable` (an object excluded for a blank or duplicate identity), `relationship-endpoint-unusable` (a relationship row of that kind ended at the object but was discarded because its other end has no usable identity).
- The later state decides finding / passed / not evaluated. The earlier state only decides presence: when it cannot be judged, a finding's presence is `unknown`, never `introduced`, and a finding of the earlier state that has no judged later state is never `resolved`.
- A v2 profile gets `aware.model-change-findings/v2`: `evaluator` (`agent`, `version`, `profileSha256`), `coverageSha256` (`base`, `revised`: the digest of each coverage file's exact bytes, or null), per rule `notEvaluated` (by reason) and `coverage` (`revisedComplete`, `baseComplete`), `scope.mode` / `scope.objects`, and `summary.unknown` with `introduced + preExisting + unknown === findings`.
- New input `validate-only`: with `check-profile-path` (and optionally `profile-path`) it validates the profile and prints an `aware.model-check-validation/v1` document with the evaluator echo and what this build supports, without reading any snapshot. `base-dir`, `revised-dir` and `profile-path` are no longer required by the manifest (they still are, unless `validate-only`).
- Needs connection-reader bridge 0.5.9 or newer.

## 0.3.0 — 2026-11-12

- `check-snapshots` gains clash: three pair rules over the solids of what a change touched and their dependency closure, as data in the check profile. `clash-overlap` (parts that pass into each other, with the thickness of the shared region measured region by region), `clash-contact` (parts that touch with no bolt or weld joining them) and `clash-bolted-plies` (a ply a bolt group names that touches no ply of the rest of its stack).
- New optional inputs `base-geometry-dir` / `revised-geometry-dir` (`geometry.json` plus GLB tiles, every sha256 verified and echoed in `inputs.geometry`); a clash profile without them is refused. New check profile block `geometry` (node mapping, tolerances, coverage qualification, bolt and weld join properties, groups, budgets); the focus file gains `sets`.
- A solid that is not fully evaluated is labelled (`approximate`, `no-geometry`, `over-budget`) and a pair involving it is `not-evaluated`, never `passed`. Output gains `focusSets`, `scope.notEvaluated`, `scope.solids` and `truncated.omitted.focusSets` when a clash rule ran. A profile without a clash rule produces the same bytes as 0.2.0.
- Clash findings can have presence `unknown` when the earlier state could not judge the pair (`summary.unknownPresence`, only when a clash rule ran); with no `clash-overlap` rule an overlapping pair is counted as not evaluated for contact instead of being dropped.
- The coverage property is found by a required profile field `geometry.qualification.propertyField` (`id` or `sourceKey`), because the app's coverage rows carry an id and no sourceKey.
- `geometry.json` may carry a `qualification` file (`{ properties: [...] }`, digest-verified and echoed in `inputs.geometry.<side>.qualification`) holding the coverage rows when the query properties do not; its rows qualify solids only and never affect what counts as changed.
- `geometry.qualification` takes a required `whenPresent` list beside `checks`: `checks` must all be present and passing, while a `whenPresent` check only has to pass when the row carries it. Needed because a coverage row holds just the checks that apply to its object's kind (a part has no `recipes-evaluated`), so requiring all of them marked every fully read part approximate.
- Uses manifold-3d 3.5.4 (Apache-2.0, WASM, single-threaded), bundled inside the connection-reader exe. Needs connection-reader bridge 0.5.8 or newer.

## 0.2.0 — 2026-11-11

- New command `check-snapshots`: runs a pinned set of data-defined checks (`aware.model-check-profile/v1`) over the objects a change touched and reports `aware.model-change-findings/v1`: findings with a recomputable `correspondenceKey` and `evidenceFingerprint`, each marked `introduced`, `pre-existing`, `pre-existing-changed` (or `-worsened` / `-improved` for a rule with a numeric metric), the findings the change resolved, and a per-identity result for objects named for a re-check (`finding`, `passed`, `not-applicable`, `excluded`, `absent`).
- Scope is every added and changed object from the full pairing (not the capped change rows) plus the named identities; everything else is stated as not checked. Pairing is the shared code of `compare-snapshots`. Counts are complete, lists are capped by the check profile and the cap is stated. Output is canonical JSON, byte-identical for the same inputs.
- First rule shape: `blank` on `entity.name`. An unknown predicate or target in a check profile is rejected.
- Needs connection-reader bridge 0.5.7 or newer.

## 0.1.0 — 2026-11-09

- New agent with one command, `compare-snapshots`: pairs the objects of two saved states of one model by a native identity the caller pins and reports added, removed and changed objects as `aware.model-change-set/v1`. Inputs are each state's `entities.json`, `properties.json` and `relationships.json`, a strict comparison profile (`aware.model-compare-profile/v1`) and an optional witness change log.
- Identity-only pairing; unpaired objects are grouped by type and name for presentation, never paired. Numeric ids never decide a change. Blank and duplicate identities are excluded with receipts, a low paired share is flagged as `discontinuity`, and placement on bounding boxes is always labelled as limited in `unchecked`.
- Counts are complete; rows, group ids and receipts are capped to profile budgets in a pinned order and reconcile. Output is canonical JSON, byte-identical for the same inputs.
- Split from `model-reference-reader` so an exact `model-reference-reader` pin and change review can share one AWARE home. Runs on connection-reader bridge 0.5.6 or newer.

# Plan Review Log: #709 microsoft-365 transport (Slice A detail, B/C outline)

Started 2026-11-01. Reviewer: Codex (read-only, adversarial).

## Round 1 — Codex

1. **BLOCKING — §2.2, §2.6: The path validator permits dot segments.**  
   `[A-Za-z0-9!._-]` accepts both `.` and `..`. URL parsing can normalize these into a different Graph route; rechecking the origin cannot detect that. Ordinary segment encoding may also leave dots unchanged.  
   **Fix:** Reject empty strings and whole-segment `.`/`..` explicitly, construct URLs with a segment-aware builder, and verify the final route structure. Add zero-network tests for both inputs, including the `drive-id: me` alternate route.

2. **BLOCKING — §2.2, §2.6: The Google digest requirements contradict each other.**  
   Today `Operation::canonical()` contains `"fields"` and no projection identifier. Replacing that with `fixed_query` and adding projection name/version changes the canonical bytes, despite the promise that FloLess’s reviewed Google digest remains unchanged. Hardcoding the old hash would conceal future semantic changes.  
   **Fix:** Specify a legacy canonical representation for the unchanged Google operation and a new representation for Microsoft. Pin the actual pre-refactor Google canonical bytes and digest. Microsoft’s digest must also cover the `me` route alternative and path-validation semantics.

3. **SHOULD — §2.1–§2.4: Identity permissions are missing from the permission model.**  
   The accepted file scopes do not themselves authorize the planned `/me` identity request. Microsoft documents `User.Read` as its least privileged delegated permission. A profile containing only `Files.Read.All` can therefore pass the operation scope check but fail identity verification; the reconnect hint names only the file scope. [Get user](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0).  
   **Fix:** Represent identity prerequisites separately from the operation’s “any one suffices” scopes. Publish and request both prerequisites, and test `Files.Read.All` without `User.Read`, including profile overrides.

4. **SHOULD — §2.1, §2.6: Scope equivalence stops at authorization and does not reach refresh generation checks.**  
   `refresh.rs` compares scopes using `keychain::normalized_scope_string()`, which preserves case and resource prefixes. A refresh changing `Files.Read.All` into its equivalent Graph URL form rotates the credential generation, and `load_slot()` refuses the call as `E_CREDENTIAL_CHANGED`. The proposed scope tests do not exercise refresh.  
   **Fix:** Define Microsoft-specific semantic scope normalization consistently for grant comparisons, or explicitly document and handle this generation change. Preserve Google’s case-sensitive behavior. Test equivalent refresh responses and genuine scope loss; reject lookalike resource prefixes.

5. **SHOULD — §2.4: The new permission metadata contains a verified factual error.**  
   The example says delegated `ChannelMessage.Send` requires admin consent. Microsoft lists **No**. Existing `config.rs` comments also incorrectly classify delegated `Chat.ReadWrite` as requiring admin consent. Tenant consent policy can still require administrator approval independently. [Permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference).  
   **Fix:** Audit every planned command against the delegated permission tables. Define `admin-consent` as the provider’s permission requirement, distinct from tenant policy. Test the new typed field’s malformed forms and omitted behavior, and state explicitly that manifest metadata never authorizes execution.

6. **BLOCKING — §2.4, §5.4: Runtime compatibility must be a release gate, not an unresolved publication choice.**  
   Removing CLI transport and marking the agent available makes older REST-capable CLIs eligible to execute its manifest mapping without the new code-owned handler. That risks raw responses and different validation behavior. Testing that other commands are planned does not protect `list-folder` itself.  
   **Fix:** Require the registry publication to follow the implementing CLI release, with `status: requires-runtime` and the correct minimum version. Test refusal on an older runtime and actual reviewed-handler dispatch on the new runtime. Also test planned-command refusal through both direct invocation and workflow entry points.

7. **SHOULD — §2.5, §2.6: The claimed workflow generation check does not exist today.**  
   `call_within()` calls `check_not_replaced()` before dispatch; `run_for_workflow_with()` does not. Saying these checks remain unchanged leaves a disconnect/reconnect window on the newly enabled Microsoft workflow path.  
   **Fix:** Add the final generation check to workflow dispatch and test replacement or disconnect after token resolution but before the data request. Identity binding can remain absent from workflows as specified.

8. **SHOULD — §2.3, §2.6: Local truncation can falsely report a complete listing.**  
   The plan truncates responses exceeding `page-size`, but sets `more-available` only from `@odata.nextLink`. A response containing extra entries without that annotation loses data while reporting `false`.  
   **Fix:** Either reject an over-limit response or report truncation whenever entries are omitted. Test that exact combination. Preserve identifiers byte-for-byte when valid; reject malformed identifiers instead of “cleaning” them into different lookup keys.

9. **SHOULD — §2.2, §§3–4: The path-input charset cannot be inherited by the outlined operations.**  
   Teams chat/channel IDs contain `:` and `@`; SharePoint composite site IDs contain commas. Worksheet names can contain spaces and other characters excluded by the proposed validator. Microsoft’s own examples demonstrate these formats. [Chat messages](https://learn.microsoft.com/en-us/graph/api/chat-list-messages?view=graph-rest-1.0), [itemReference](https://learn.microsoft.com/en-us/graph/api/resources/itemreference?view=graph-rest-1.0).  
   **Fix:** Make validation operation/input-specific. Keep opaque IDs separate from worksheet names and OData function arguments, encode each appropriately, and add real-format round-trip fixtures before B/C inherit this abstraction.

10. **SHOULD — §4: Expanded replies need independent bounds and completeness reporting.**  
    `$top ≤ 50` bounds root messages, not expanded replies. Graph documents separately paginated replies through `replies@odata.nextLink`. Channel ordering uses the modification time of the entire reply chain, so filtering solely on the root’s timestamp can discard an old thread containing a recent reply. [Channel messages](https://learn.microsoft.com/en-us/graph/api/channel-list-messages?view=graph-rest-1.0).  
    **Fix:** Define whether `since` applies to messages, replies, or threads; bound total projected messages/replies and bytes; expose root and reply truncation. Test an old root with a recent reply and nested continuation. The proposed chat filter/order pairing and 50-message ceiling are correct.

11. **SHOULD — §§3–4: Query support must be specified per endpoint.**  
    The abstraction encourages fixed `$select` everywhere, but `/me/joinedTeams` supports no OData customization. Channel messages support `$top` and `$expand`, while chat messages support the documented `$top`/`$orderby`/`$filter` subset; neither supports a universal `$select`. [Joined teams](https://learn.microsoft.com/en-us/graph/api/user-list-joinedteams?view=graph-rest-1.0), [Chat messages](https://learn.microsoft.com/en-us/graph/api/chat-list-messages?view=graph-rest-1.0).  
    **Fix:** Add an endpoint-specific query-support matrix and exact-wire tests. For endpoints without server-side page sizing, enforce local bounds and report truncation truthfully.

12. **SHOULD — §3: Two “read” branches require write-capable OAuth grants, and Excel remains insufficiently bounded.**  
    Microsoft documents delegated `Files.ReadWrite` for both worksheet range retrieval and sharing-link access. The Slice A `Files.Read.All` grant therefore cannot be assumed sufficient for either branch. An A1 grammar alone also permits enormous ranges. [Worksheet range](https://learn.microsoft.com/en-us/graph/api/worksheet-range?view=graph-rest-1.0), [Shared items](https://learn.microsoft.com/en-us/graph/api/shares-get?view=graph-rest-1.0).  
    **Fix:** Declare branch-specific scope requirements and explain the broader grant before consent. Bound rows, columns, total cells, and cell text; reject oversized ranges before networking. Define sharing-link redemption behavior and prohibit permission-granting headers in the reviewed read.

13. **SHOULD — §2.6: The new security boundary needs behavioral tests, not just host-list assertions.**  
    Checking that production URLs contain Graph/login hosts does not prove rejection of attacker origins, refresh redirects, profile changes between validation and refresh, or token-bearing error echoes. Google fixtures alone do not exercise the new Microsoft provider branch.  
    **Fix:** Run Microsoft fixtures through capabilities, bound calls, and workflows. Assert zero requests to attacker sinks, test identity/data/refresh redirects, and inspect failures and logs for access-token and refresh-token sentinels. Validate tenant substitutions as tenant identifiers; `token_endpoint_is_own()` currently compares against a string constructed from an unvalidated tenant.

14. **NIT — §2.1: Resolve the identity question using Microsoft’s documented contract.**  
    `oid` alone is supported for per-user identity; Microsoft says it is unique, non-reusable, and different across tenants. `tid:oid` is not required merely to prevent speculative GUID collisions. Graph nevertheless specifies user `id` as opaque, so a GUID-only parser would be inappropriate. [Identity claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference), [User resource](https://learn.microsoft.com/en-us/graph/api/resources/user?view=graph-rest-1.0).  
    **Fix:** Commit to exact opaque `/me.id`, reject malformed values without rewriting them, and test personal accounts, guest accounts, changed UPN with unchanged ID, and changed ID with unchanged UPN.

## Round 2 — Codex

1. **SHOULD — §R.5, §2.4: The admin-consent correction introduces another factual error (R1-5).**  
   §R says delegated `Sites.ReadWrite.All` requires admin consent. Microsoft’s delegated column says **No**; the application column says Yes. This affects permission metadata being added in Slice A, including planned commands.  
   **Fix:** Correct this statement and the `config.rs` comment; audit each permission individually against the delegated column. Add explicit expected-value tests rather than only checking that manifest and code agree. [Microsoft permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference#sitesreadwriteall).

2. **SHOULD — §R.3, §2.6: Missing identity scope still needs an explicit capability-flow change (R1-3).**  
   Today `capabilities_within()` calls `read_identity()` before evaluating scopes. With `Files.Read.All` but no `User.Read`, `/me` can fail first, producing `identity-unverified` and bypassing the promised `scope-missing` reconnect hint. Adding `identity_scopes` to the existing post-identity predicate is insufficient.  
   **Fix:** Check identity prerequisites before `/me`, define the unverified credential shape returned with `scope-missing`, and test this through capabilities as well as bound calls. Assert zero identity/data requests when the prerequisite is absent. [Get user permissions](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0).

3. **SHOULD — §R.3 versus §2.4: Published permission metadata still omits the identity prerequisite (R1-3).**  
   The manifest example publishes only `[Files.Read.All]`, and its consistency test compares against `request_scope`. The new capability `permissions` object likewise has no specified identity-scope representation. A consumer following this metadata can request exactly the advertised grant and still be unable to verify the account. The corrected reconnect sentence does not fix initial consent discovery.  
   **Fix:** Publish either the complete requested set `[User.Read, Files.Read.All]` or separate identity and operation scopes with explicit combination rules. Update the consistency tests to cover both requirements.

4. **SHOULD — §R.6, §2.7: The runtime floor prevents the proposed worktree E2E unless version staging changes (R1-6).**  
   The repository builds as `0.165.0`, while the revised manifest requires `0.166.0`. `CURRENT_CLI_VERSION` comes directly from Cargo, so the implementing worktree build will refuse installation/capabilities before reaching the reviewed handler. Deferring registry publication does not resolve local validation.  
   **Fix:** Specify when the implementing crate becomes `0.166.0`, or use an explicit development-manifest staging approach and apply the final floor during publication. Run the live gate against the final manifest with a build satisfying its floor; retain the older-runtime refusal test.

5. **SHOULD — §R.9, §2.6: Refresh-redirection coverage remains missing (R1-13).**  
   The revised attacker-sink list covers identity/data redirects, profile overrides and profile replacement, but omits a redirect returned by the validated refresh endpoint. The refresh implementation currently disables redirects; the promised behavioral test must protect that boundary independently of GET redirects.  
   **Fix:** Add expired-token fixtures returning refresh 302 and 307/308 responses to an attacker sink. Assert zero sink requests, no identity/data dispatch, and absence of refresh-token, access-token and client-secret sentinels from failures and logs.

6. **NIT — §R carried items, §3: The sharing-link carry-forward loses part of R1-12.**  
   The carry records broader grants and range bounds, but does not retain the requirement to define redemption behavior and prohibit permission-granting headers. Microsoft’s sharing endpoint documents `Prefer: redeemSharingLink`, which grants durable access.  
   **Fix:** Explicitly carry the prohibition on durable redemption into the B addendum and require an exact-header test before classifying that branch as a reviewed read. [Sharing-link headers](https://learn.microsoft.com/en-us/graph/api/shares-get?view=graph-rest-1.0#request-headers).

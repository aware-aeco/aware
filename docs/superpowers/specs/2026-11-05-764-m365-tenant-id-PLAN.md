# #764 — the verified Microsoft principal carries its tenant id

## Goal

`aware agent call-capabilities microsoft-365 <read>` returns
`credential.principal.tenant_id` (the Entra directory GUID; the consumer tenant
`9188040d-6c67-4c5b-b112-36a304b66dad` for a personal Microsoft account), obtained
from Microsoft during the same live verification that reads `/me`. `stable_id`
stays the `/me` `id` (oid). The binding id covers (oid, tenant), and `aware agent
call` re-verifies both at dispatch and refuses (`E_BINDING_CHANGED`, nothing read)
when either differs. Google is unchanged: `tenant_id` is `null`, its binding id is
byte-identical.

## Where the tenant comes from — options weighed

1. **`tid` claim of the access token.** Rejected. Microsoft documents access
   tokens as opaque to clients ("Clients use the token but shouldn't understand or
   attempt to parse it"), Graph tokens are in a proprietary format, and a
   personal-account Graph token is not a decodable JWT at all.
2. **`tid` claim of the ID token.** Rejected as the primary source: AWARE's
   microsoft-365 grant requests no `openid` scope, so no existing sign-in ever
   received an ID token; it would need a scope change and every person to sign in
   again, and AWARE stores no ID token today.
3. **`GET /v1.0/organization?$select=id` under `User.Read`.** Chosen for work and
   school accounts. Documented for delegated work/school access with `User.Read`
   (which returns `id`, `displayName`, `verifiedDomains`), and the built-in Guest
   User and Restricted Guest User roles are listed, so it answers for members and
   guests alike. It answers the directory the token was issued in — the same
   directory whose user object `/me` returned — so the (oid, tenant) pair is
   consistent even for a guest (where a home-tenant value would not be). It is a
   live read with the same token, same origin, same deadline, no new scope.
   Microsoft documents it **"Not supported"** for personal Microsoft accounts
   (observed: `200 {"value":[]}` historically, `500 "Unable to find target
   address"` more recently).
4. **For a personal account only: the token endpoint's own answer.** When
   `/organization` names no single organisation, AWARE performs one refresh-token
   grant through the already-pinned Microsoft token endpoint with `client_info=1`
   (the parameter every MSAL library sends; the reply's `client_info` is
   base64url JSON `{uid, utid}`), and reads `utid` (or, if the grant happens to
   carry an ID token, its `tid`). The tenant is accepted from this source **only
   if it is the consumer tenant GUID**. Any other value (an Entra tenant whose
   `/organization` read failed transiently, a guest's home tenant) is not used:
   the credential is reported unverified (`identity-unverified`) and `call` fails
   with `E_CALL_IDENTITY_FAILED` reason `tenant`. The refresh is stored back to
   the same slot through the existing compare-and-store, keeps the generation
   (same grant), and is the same credential maintenance the resolver already
   performs.

Nothing is guessed: a personal account is never inferred from an id's format or
from an error.

## Binding

`binding_id(integration, slot, sub, tenant: Option<&str>)`: with `None` the hash
input is exactly today's (Google ids unchanged); with `Some(tid)` the lowercase
tid is hashed as one more NUL-terminated part. Existing microsoft-365 binding ids
change once (FloLess's R6.8 consumer has not shipped). Same oid in a different
tenant → different binding id.

## Dispatch

`call` re-reads `/me` and the tenant exactly as above, recomputes the binding, and
on a mismatch returns `E_BINDING_CHANGED` (exit 6) before the data request; there
is no fallback to an oid-only comparison.

## Not changed

- Operation digests (`operationSha256`) — the identity procedure is per provider;
  the pinned digests FloLess reviewed stay byte-identical.
- The workflow / `agent invoke` path (no identity step there).
- Google Workspace: `principal.tenant_id: null`.

## Tests

- caps: tenant present (member), guest (org read answers the resource tenant),
  personal account (org read fails → token endpoint `client_info` consumer
  tenant), personal path with a non-consumer `utid` → unverified, org read with
  two/zero orgs or a non-GUID id → personal path.
- call: tenant changed between caps and call → `E_BINDING_CHANGED`, no data
  request; same oid other tenant → different binding id.
- binding: Google id unchanged (pinned), Microsoft id differs per tenant.
- token_response: `client_info` / `id_token` tenant parsing, malformed inputs.

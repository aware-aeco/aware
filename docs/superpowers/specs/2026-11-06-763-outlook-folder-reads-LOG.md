## Codex round 1

Reviewed rev 1 against issue #763, the #709 plan, `agent_call.rs`, the M365 fixture tests, and current Microsoft documentation. These are plan findings; no implementation or live mailbox tests were performed.

1. **blocker — §§0, 1, 2, 7 L6: `received-after` does not provide a complete folder sync.** The filter is encoded into the continuation state, so it persists beyond the first request. An old message moved into the folder can remain outside that filter, defeating the very reason for adopting delta. Independently, Microsoft documents a maximum of 5,000 messages for filtered message delta. A successful final cursor is therefore insufficient evidence that the desired initial population was enumerated. See [message delta synchronization](https://learn.microsoft.com/en-us/graph/delta-query-messages). **Fix:** make the Knowledge synchronization stream unfiltered. Remove this input from the completeness-preserving command, or explicitly separate a limited filtered read from full synchronization. If a time window is a product requirement, enumerate unfiltered changes and apply a documented local inclusion policy. Never reconcile a filtered reset as a complete-folder snapshot. Test an older-than-cutoff message moved in after baseline and a population exceeding the documented filtered limit.

2. **blocker — §§1, 3 delta rule 1, 5.2–3: fixed page size plus the byte cap can permanently wedge synchronization.** Fifty header records are not bounded to approximately 100 KB: recipient collections alone can exceed the 1 MiB raw-read cap, before projection reduces them. Even projected records retaining 50 To and 50 Cc names/addresses can exceed the output cap across 50 messages. `read_data()` currently applies the caller's cap to the raw response too; the plan raises the raw cap only for get-message. Keeping the old cursor prevents accidental advancement but provides no way to read this page, and the fixed header cannot be reduced by a caller. Dropping maxpagesize on the claimed fallback also relies on an unverified default of 10. **Fix:** define separate bounded raw/output budgets for delta and a recovery protocol. Permit a typed page-size preference, including on cursor requests, rendered into the single code-owned Prefer header; do not locally cut a returned page. Prove whether retrying the same cursor with a smaller preference works. Define a safe terminal/incomplete outcome for a single unprocessable record rather than promising every stream can progress. Test oversized raw/small projected pages, oversized projected pages, same-cursor recovery, and the one-record case.

3. **blocker — §§2, 3 delta rules 1 and 3, 6: `omitted` contradicts “never cut a delta page.”** A malformed upsert or tombstone is dropped while a usable next/delta cursor is returned. Advancing loses that change permanently; losing a tombstone can retain deleted or recalled content forever. Counting the loss does not repair it, and the proposed malformed-id test would bless the defect. **Fix:** an unrepresentable change must prevent a successful completeness/advancement result, or participate in an explicit durable quarantine/reconciliation protocol that the consumer must acknowledge. Distinguish harmless withheld optional fields from a lost entity change. Fixtures must place an invalid upsert and invalid removal between valid records and prove the caller cannot silently commit past them. State how this failure is resolved without an endless retry of the same poison page.

4. **major — §§2, 3, 5: the output and input ID contracts do not round-trip, and a shared fix could silently change old operations.** Existing `exact_id()` at `agent_call.rs:2711` accepts up to 256 bytes and permits punctuation that the proposed 512-byte Outlook input rejects. Using it for removals drops accepted 257–512-byte Outlook IDs; using it for messages/folders can emit an ID that cannot be passed back. `Entry::text` also cleans/truncates identifiers if reused for conversation or parent IDs. Conversely, globally widening `exact_id()` changes existing projection behavior without changing those rows' digests. **Fix:** introduce Outlook-specific exact validators with matching input/output byte limits and grammar, preserve case and bytes for every lookup/join ID, and never pass IDs through display-text reduction. Specify independent handling for conversation IDs, internet message IDs, parent folder IDs, and attachment IDs. Separate folder aliases from message IDs explicitly. Test 256/257/512/513-byte boundaries, punctuation, padding, case, and every emitted lookup ID being accepted by its destination input. Keep old validators and old-row behavior intact.

5. **blocker — §3 delta shape and rules 5–6: update/duplicate/conflict semantics are missing.** The plan splits Graph's change sequence into `messages` and `removed`, losing their interleaving, and gives no rule for the same ID in both or repeated across pages. It also treats absent type as message and suggests reusing entry rules that default missing booleans to false; sparse updates could erase existing headers, recipients, kind, or attachment flags. Microsoft permits repeated entities and describes updates containing at least changed properties, with no general ordering guarantee. See [delta resource representation](https://learn.microsoft.com/en-us/graph/delta-query-overview). **Fix:** define whether entries are full replacements or patches, preserve presence/null semantics, and never default missing update fields into authoritative values. Use a unified change list or an equivalent explicit conflict representation. Define conflict resolution through authoritative reads/reconciliation; do not assume “removals always win” or that service order is a reliable version order. Test ID-only updates, read-only updates, repeated upserts, remove/re-add in both orders, and cross-page replays. Pin how unknown/absent kind is merged.

6. **major — §§1, 3 get-message, 4: hydration is a second, racing read with no consistency or checkpoint contract.** After delta returns an ID, mailbox-wide `GET /me/messages/{id}` can still succeed after that mail moved out of the selected folder. It can also return a newer body than the delta headers, or fail transiently after the consumer has saved the cursor. Advancing and merely labelling a body unread can make that failure permanent if no later change occurs. **Fix:** document a consumer protocol that durably records page changes and pending body work before committing the cursor, retries transient hydration failures independently, and makes tombstones cancel pending work. Expose an exact message version such as `changeKey` and, if membership verification is required, `parentFolderId`, or provide a reviewed folder-scoped read. Reconcile version/membership disagreements and ensure late body results cannot resurrect a removed source item. Specify terminal oversized/404 outcomes separately from retryable failures. Test crash-after-cursor, move/delete between reads, newer-version hydration, and late completion after removal.

7. **major — §§2, 3 delta rule 2, 7: the cursor protocol assumes undocumented restrictions and does not identify its synchronization context.** Microsoft instructs clients to reuse the returned URL; its message examples do show token-only query strings and equivalent parenthesized/segment path forms, but do not guarantee forever that every token is unreserved ASCII, at most 4,096 bytes, or that every link has exactly one query pair. Rebuilding from only the token is a compatibility assumption to gate explicitly, not a documented promise. The bare `skip:`/`delta:` value also carries no contract version, folder, account binding, initial filter, or projection identity; a consumer cannot tell incompatible persisted streams apart. Arbitrary externally obtained Graph tokens can encode query options other than this operation's reviewed selection. See [message delta parameters and continuation guidance](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0). **Fix:** define a versioned opaque cursor scoped to the operation/projection, resolved folder, binding, and initial options, with a clear trust/provenance policy. If the code promises to enforce cursor provenance, authenticate it rather than trusting caller-editable metadata. Encode token bytes reversibly using a bounded transport-safe envelope; decode/encode URL query values exactly once. Retain code-owned routes and never follow a provider link. Explicitly gate token-only reconstruction across both skip and delta requests, document supported link shapes and a recoverable incompatibility outcome, and reject route/context mismatch without exposing links or tokens in errors.

8. **major — §§4, 5.4, 6: 410 alone is not a complete dead-state mapping.** Microsoft documents 410 resets and expired Outlook tokens returning a 40X response with codes such as `syncStateNotFound`; the latter can become a generic 404 indistinguishable from a deleted folder under this plan. Existing `get_bounded()` discards error bodies before `read_data()` can classify them. See [delta reset and token duration](https://learn.microsoft.com/en-us/graph/delta-query-overview). **Fix:** specify a small bounded error-code parser and an allowlisted, operation-specific mapping for confirmed dead-state codes/statuses. Return only code-owned classifications and numeric status, never provider messages, headers, URLs, or raw JSON. Do not classify every 404 as expired. Test 410, expired-state 40X with a recognized code, actual folder-not-found, malformed/oversized error bodies, and secret-bearing error text. Reset must stage an unfiltered full rescan and remove unseen items only after successful completion, not at its start or after one page.

9. **major — §§1, 3 get-message, 7 L5: attachment support has an ambiguous fallback and incomplete completeness metadata.** Generic GET/OData support does not by itself establish that this exact nested attachment `$select` works for delegated v1.0 across attachment types. L5 only asks for names/no bytes, not that the server omitted payloads on the wire. Unexpected payloads can exhaust the raw cap before `content-withheld` can be projected. An expanded collection may also be partial; `attachments-omitted: 0` cannot mean complete when there is a nested continuation. Dropping expand after the live check changes the advertised contract and reviewed query; `hasAttachments` alone is insufficient even to describe inline attachments. Microsoft documents that [hasAttachments excludes inline-only attachments and uniqueBody requires selection](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0). The uniqueBody selection itself is appropriate. **Fix:** settle the exact query before freezing the operation digest; fallback is a plan/contract revision, not an automatic undocumented behavior switch. Model attachment metadata as complete/partial/unavailable, report nested continuation without following it, and distinguish omitted-known records from unknown remaining records. Live-test file, item, reference and inline attachments, an attachment larger than 8 MiB with a small body, exact metadata projection, and unexpected contentBytes/item payloads. Prove the small-body read survives large attachments.

10. **minor — §§1, 3 folders, 7 L1: folder pagination cannot be safely driven from the specified output alone.** `more-available` plus caller-supplied `skip` gives no authoritative next offset. Advancing by returned folder count repeats positions when malformed folders were omitted; advancing by requested page size assumes Graph filled the page. Local cuts further complicate the consumed offset. A continuation beyond 10,000 is unrepresentable. The documented childFolders API supports OData options and excludes hidden folders by default; `msgfolderroot` is a documented well-known root, so that route is reasonable. See [childFolders](https://learn.microsoft.com/en-us/graph/api/mailfolder-list-childfolders?view=graph-rest-1.0) and [well-known folders](https://learn.microsoft.com/en-us/graph/api/resources/mailfolder?view=graph-rest-1.0). **Fix:** expose a code-owned validated continuation/next-skip with defined bounds and an explicit limit-reached outcome, preserving the no-link-follow rule. State the hidden-folder policy. L1 must force multiple pages both at root and beneath a folder and prove no omissions/repeats with short pages and locally rejected entries; seeing one folder is insufficient.

11. **major — §7 L2–L6: the live gate can pass without exercising the risky paths, and some assertions are invalid.** A folder with only three messages need not produce any skiptoken at page size 50. L3 needs at least four controlled message roles and calls moved-in IDs “new” while L4 requires immutable identity. A quiet delta response need not return a different token, and replay/eventual-consistency behavior makes immediate empty/unchanged assertions unreliable. Header acceptance alone does not prove immutable tombstones or page-size behavior. The combined header is a reasonable HTTP representation, but must actually retain both preferences on every data page; [immutable-ID documentation](https://learn.microsoft.com/en-us/graph/outlook-immutable-id) requires the preference per request and limits stability to the same mailbox. **Fix:** use isolated, labelled seeds and a guaranteed multipage baseline; verify both continuation kinds preserve selection, IDs and initial options. Require a valid reusable final token, not token inequality. Match mutations by recorded IDs with bounded visibility retries. Check unchanged immutable ID across a same-mailbox move and that tombstones use the baseline ID. Add successful new delivery, old-mail move-in, read/unread, body edit, deletion, and successful recall. A confirmed cloud recall deletes the recipient copy; Graph removal should be tested after that success, not inferred from a recall request. See [cloud recall behavior](https://learn.microsoft.com/en-us/exchange/mail-flow-best-practices/work-with-cloud-based-message-recall). Explicitly hold implementation acceptance until these gates pass or scope is revised.

12. **major — §6: the proposed negative controls do not establish their claimed regressions, and digest pins are insufficient.** Merely setting `limit_input` cannot make a deliberately unbounded delta projection cut records; without a matching input or a projection that uses the limit, that mutation can leave the test green. A hand-built 120-entry projection fixture also does not exercise raw caps, HTTP decoding, serialization caps, or cursor checkpointing. New digest literals alone do not prove `read_cap` or new cursor semantics are digest-bound. Existing `rows_shipped_before_b2_keep_their_digests()` enumerates all rows except Excel/shared-item, so adding Outlook rows makes that old snapshot fail even when every shipped digest is unchanged. **Fix:** capture all pre-change row digests/canonical forms, including B2, independently of the new table; scope old snapshot membership without updating away old pins. Add mutation assertions that changing read_cap, cursor grammar/location, fixed headers/query or projection changes the new digest. Inject an actual cut into the delta projection and demonstrate the whole-page assertion fails. Add end-to-end fixture tests for the failures above plus zero-request refusal of raw OData/URL inputs and sentinels in raw bodies, links, headers and errors, asserting no sentinel reaches output/errors/logs. Guard old projection behavior as well as old digest bytes when sharing helpers.

13. **major — §§0, 3–4, 8: “erasable” is a consumer requirement with no handoff contract.** These reads enable deletion detection but do not make already-created immutable Knowledge versions erasable. Tombstones must remove current source membership while Erase must also account for historical versions, derived chunks/indexes, hydration queues, cached bodies/previews, and persisted cursor state. A late sync or body fetch can otherwise recreate data after Erase. This does not require adding a Microsoft write operation; erasure concerns the consumer's stored copies. **Fix:** add explicit integration obligations and a consumer acceptance gate: source/generation identity fences late results; page and cursor commits are durable/idempotent; Remove/Pause/Erase have distinct retention behavior; Erase invalidates pending work and purges every retained derivative/history copy covered by the product promise. Verify erase while a page/body read is in flight and after multiple immutable versions. If these guarantees belong wholly to slice 1b, name that dependency and stop claiming the three read commands alone satisfy the lifecycle.

VERDICT: REVISE 13 findings

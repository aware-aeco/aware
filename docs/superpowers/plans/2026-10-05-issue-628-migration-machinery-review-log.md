## Round 1 — Codex
The plan needs revision. I could read the plan and repository, but GitHub issue #1985 was unavailable through both the browser and local GitHub CLI, so I assessed the owner rules as summarized in the plan.

- **The AI approval tripwire is ineffective.** Section 11 requires `--front-door` for `--person`, but rejects an AI session only when that flag is *absent*; an AI can supply the flag and claim a person approved. **Fix:** Require a verifiable approval tied to the candidate digest, from a person controlled front door, before accepting person promotion or policy creation. [Plan §11](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:136>)
- **`app compile` bypasses the proposed approval boundary.** It writes a fresh original lock, while section 11 only records a front door when one is given; an AI process could recompile changed agent bytes without using migration approval. **Fix:** Apply the same person or approved policy authorization to any command that replaces executable lock bytes. [Plan §5 and §11](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:78>)
- **The approval reference does not identify what was approved.** A batch ID, actor name and front door claim do not bind a person’s decision to the candidate’s exact plan and package digests. **Fix:** Record and verify an approval for the exact candidate digest and base lock digest before replacement. [Plan §7](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:97>)
- **Promotion does not specify revalidation of the candidate’s compiled plan.** Hashing candidate bytes and verifying target packages detects a changed file, but does not establish that its nodes, unchanged agents, safety result and evidence came from `compile_candidate`; a replacement candidate can have a new matching hash. **Fix:** Under the promotion lock, recompile from the current source and pinned packages and require an exact candidate plan match. [Plan §7](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:102>)
- **A missing original archive still permits a successor to run.** Reporting it only in `app check` cannot substantiate the claim that the original approval record was preserved. **Fix:** Fail run and promotion when a successor’s original archive is missing or its bytes do not match `approval.original.lock-digest`. [Plan §5](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:75>)
- **Chain checks leave room for inconsistent history.** They compare the last `to` with top-level values only for moved agents and check its plan digest against the current lock; they do not verify each earlier successor against the lock bytes and evidence it cites. **Fix:** Verify every link’s archived `from-lock-digest`, evidence digest, full pin maps and resulting plan digest before labeling or running a successor. [Plan §5](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:75>)
- **Windows crash recovery is underspecified.** A create-new `.promote.lock` can remain after a crash and block later promotion; the stated fsync and rename sequence also lacks a recovery rule for staged files and an interrupted replacement. **Fix:** Specify a recoverable transaction state, stale sentinel recovery, same-volume replacement and fault tests at each durability step. [Plan §7](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:102>)
- **The labels overstate provenance.** “Approved by `<actor>`” presents an unverified CLI claim as a verified human act, and “read-only” relies on manifest declarations rather than observed effects. **Fix:** Label these as *claimed person approval* and *declared read-only*, including the unverified status in run records. [Plan §11](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:134>)
- **The PR2 state machine can mislead callers.** Its planned `auto-under-policy` state conflicts with section 11’s ruling that no v1 comparison can produce an eligible executed `Pass`. **Fix:** Make PR2 report `needs-person` for every real candidate until an executed fixed-state method ships or the owner explicitly ratifies static inspection. [Plan §7 and §11](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:95>)
- **The PR3b safety dependency is stated but not gated.** The FloLess CLI-version gate and hold-list must ship first, while older AWARE can run promoted top-level pins without successor labels. **Fix:** Make the FloLess gate and hold-list a release prerequisite verified before PR3b can ship. [Plan §11](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:139>)

## Round 2 — Codex
Section 12 closes several earlier gaps, but I still find four blockers:

- **A person approval is still self-asserted.** A same-user AI process can write the unsigned `--approval` JSON with matching digests and a claimed front door; `attested: false` makes the label honest but does not enforce “AI never approves.” **Fix:** Require a front door attestation that the CLI can verify before accepting person promotion or policy creation. [§12, line 144](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:144>)
- **Promoting a backing app changes its callers before they approve it.** The plan warns and proceeds, while current resolution loads the backing app’s effective lock for a caller’s run; that caller can therefore execute new nested bytes while retaining its old approval record. **Fix:** Block backing app promotion until affected callers are held or their successor approvals are committed as part of the change. [§11, line 137](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:137>)
- **The chain digest rule cannot validate multiple successors as written.** Each link’s `to-plan-digest` cannot equal the *current* `plan_digest(lock)` after a later promotion; checking only the last link leaves earlier plan digests unverified. **Fix:** Archive each resulting lock, verify each link against its own resulting plan, and compare only the last link with the current lock. [§12, line 148](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:148>)
- **The release gate does not cover direct older-CLI runs.** The FloLess version gate protects FloLess calls, but the plan says AWARE 0.149 will run a promoted lock’s new top-level pins while silently ignoring its successor record. **Fix:** Make promoted locks unreadable to pre-#628 CLIs, or constrain promotion to an installation where every run entry point enforces the minimum CLI version. [§5, line 77](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:77>)

## Round 3 — Codex
Section 13 fixes the chain and older-CLI issues from my last review. **Attestation is not the only remaining issue.** The backing-app rule still has two concrete run-path gaps:

- **The proposed multi-app promotion is not atomic to runners.** Windows replaces the lock files one at a time, and `app run` does not participate in transaction recovery. A run between replacements, or after a crash before recovery, can see a new backing lock with an old caller lock. **Fix:** Make runs wait on and recover the shared transaction before preflight, or publish the set through one atomic commit pointer. [§13, line 156](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:156>)
- **A held caller can still run.** The plan defines `HOLD` as a promotion refusal, yet section 13 treats a caller being on hold as sufficient to promote its backing app alone. That caller can then execute the new backing bytes under its old lock. **Fix:** Make this hold block caller runs until caller approval, or require every runnable caller in the joint promotion. [§6, line 87](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:87>) [§13, line 156](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:156>)

**Attestation remains an explicit owner-level disagreement:** the unsigned person record binds a claim to exact bytes, but the CLI cannot distinguish a front-door click from a same-user process that wrote the record. I accept that a key readable by the same user would not solve that. **Fix:** Have the owner explicitly accept the front door as the trust boundary for “AI never approves,” or specify an enforceable separated boundary before shipping person promotion. [§13, line 159](</C:/Users/bimst/source/repos/aware-1985-migrate/docs/superpowers/plans/2026-10-05-issue-628-migration-machinery-plan.md:159>)
